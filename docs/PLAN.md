# 开发计划与阶段边界

## 第一阶段：基础工程

Vue 3、TypeScript、Router、Pinia、Tailwind 与 Cloudflare Vite 插件。移动端首页、校区切换、模拟搜索、模拟菜品详情、临时口味画像和 Worker 健康检查。所有菜品、价格、评分和评价均为测试数据，不能用于真实就餐判断。校园名称只表示未来覆盖范围。

假设：首期食堂未指定，因此使用“示例食堂 A”，不虚构真实窗口。模拟评价不进入数据库。口味匹配与 AI 预测分本阶段均不计算。画像仅保存在当前浏览器，可一键删除，不包含身份凭证。其余校区显示待开放空状态。

## 第二阶段：完成 P0 数据与身份闭环

1. 确认首期真实食堂、窗口和经核实的菜品资料。
2. 添加 D1 Migration：users、user_sessions、taste_profiles、campuses、canteens、stalls、dishes、reviews、review_images、reports、audit_logs；统一 UTC 时间、外键、索引与用户/菜品唯一约束。示例 Seed 仅用于本地。
3. 实现公开 API、分页与参数验证，替换前端模拟数据服务。
4. 对接可替换的邮箱验证码服务：验证码哈希、有效期、发送与验证限流；服务端会话、HttpOnly/Secure/SameSite Cookie、CSRF 与注销。未配置认证时生产写入保持关闭。
5. 评价增删改与服务端授权；好吃程度与感知维度独立；贝叶斯平滑 k=20 可配置，明确同类基准与低样本规则。
6. D1 私密口味画像、删除流程、昵称与个人评价管理。
7. 管理员服务端权限、内容审核、举报、审计记录、重复菜品处理。
8. 集成测试覆盖跨用户越权、重复评价、SQL 参数、会话过期、CSRF、限流与环境隔离。

## 后续 P1 / P2

P1：R2 上传鉴权、类型/实际内容/体积检查、限流和内容安全流程，再开放图片；排行榜、筛选、运营统计、满足最小样本要求的地域分组统计、PWA。

P2：有足够真实样本后实现口味匹配与相似用户推荐、多校区与趋势。不得展示无依据的预测分。

## 上线门槛

当前项目不具备公开开放评价的条件。上线前补齐隐私政策、协议、数据删除、备份恢复、错误日志脱敏、内容治理和适用运营要求的核对；测试校园网、微信和移动网络的真实访问。生产资源、域名、付费服务与部署都需要单独授权。GitHub Actions 仅检查与构建，不部署、不操作远程数据库。
